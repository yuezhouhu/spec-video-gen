## Project

Krea Realtime 14B — real-time video generation using a 14B diffusion model distilled from Wan 2.1 via the Self-Forcing technique. Generates video at 11 fps on NVIDIA B200 GPUs with 4 inference steps. Non-commercial license (CC-BY-NC-SA-4.0).

## Speculative Decoding with ImageReward Routing

### Algorithm Overview

The system uses speculative decoding for video generation: a small **drafter** model generates candidate blocks cheaply, and an **ImageReward** quality scorer decides whether to accept the draft or reject it and re-generate with the full **transformer** (target model). This trades off speed for quality — accepting more drafts is faster but lower quality.

### Routing Algorithm Details (Reward v2.5)

The routing logic lives in `release_server.py`, function `GenerationSession.generate_block_internal()` (around line 960). It has four components:

1. **Force-reject first block**: Block 0 (the first block of each video) is always generated by the transformer, never the drafter. The first block establishes the scene, subject, and composition — these are critical for VisionReward's text-video alignment questions. Controlled by `REWARD_FORCE_REJECT_FIRST` env var (default `true`).

2. **Min-frame scoring**: For blocks 1+, the draft is VAE-decoded and each frame is scored with ImageReward (`_score_frames_image_reward()` at line ~136). The function returns both the average and minimum frame scores. The **minimum** score is used for the accept/reject decision (controlled by `REWARD_SCORE_MODE=min`). This catches blocks where even one frame is bad — the average might mask a single terrible frame, but min-frame ensures it gets rejected.

3. **Threshold modes** (`REWARD_THRESHOLD_MODE`):

   - **`dynamic`** (default, v2 behavior): Global running-percentile threshold. All min-frame scores from all prompts are pooled into `_routing_stats["scores"]`. The threshold is the empirical quantile at `(1 - effective_accept_rate)`. The effective accept rate is auto-adjusted upward to compensate for the forced-reject first block:
     ```
     effective_accept_rate = (REWARD_ACCEPT_RATE × num_blocks) / (num_blocks - 1)
     ```
     With `REWARD_ACCEPT_RATE=0.72` and `num_blocks=9`: effective = 0.72×9/8 = **0.81** for scored blocks, yielding ~72% overall acceptance. During warmup (< 5 scores), a Gaussian prior threshold is used: `N(mean=0.566414, std=1.070617)` at the `(1 - effective_accept_rate)` quantile.

   - **`fixed`** (v2.5): Constant threshold set at startup via `REWARD_FIXED_THRESHOLD`. No warmup phase, no score pool dependency — every scored block uses the same threshold from block 1 onward. Default value **-0.7769** is the empirical 19th percentile from a 200-prompt MovieGenVideoBench run (eff_accept=0.81, score_mode=min, 792 scored blocks). Use this mode for deterministic routing behavior across runs.

4. **VAE cache management**: Before scoring, the decode cache is cloned. If the draft is accepted, the new cache from draft decoding is kept. If rejected, the saved cache is restored so the transformer's output can be decoded cleanly.

### Routing Env Vars

| Var | Default | Purpose |
|---|---|---|
| `USE_IMAGE_REWARD` | `true` | Enable/disable ImageReward model loading |
| `REWARD_THRESHOLD_MODE` | `dynamic` | `dynamic` = v2 running-percentile, `fixed` = v2.5 constant threshold |
| `REWARD_FIXED_THRESHOLD` | `-0.7769` | Constant threshold when `REWARD_THRESHOLD_MODE=fixed` (empirical 19th pctl from 200-prompt run) |
| `REWARD_ACCEPT_RATE` | `0.72` | Target overall accept rate (only used in dynamic mode) |
| `REWARD_FORCE_REJECT_FIRST` | `true` | Force block 0 to use transformer |
| `REWARD_SCORE_MODE` | `min` | `min` = worst-frame score, `avg` = mean-frame score |
| `REWARD_GLOBAL_MEAN` | `0.566414` | Prior mean for dynamic warmup Gaussian threshold |
| `REWARD_GLOBAL_STD` | `1.070617` | Prior std for dynamic warmup Gaussian threshold |
| `OUTPUT_DIR` | `outputs/samples` | Output directory for `sample_run.py` |

### Benchmark Results (200 prompts from MovieGenVideoBench, 832×480, seed=42, 9 blocks/prompt, RTX A6000)

| Mode | Accept Rate | VisionReward | Avg Time/Video | Speedup |
|---|---|---|---|---|
| **Reward v2.5 dynamic** | **65.2%** | **0.0691** | **71.1s** | **1.62x** |

Reward v2.5 dynamic **matches** target-only quality (0.0691 vs 0.0696, within -0.7%) while being 1.62x faster. The routing selectively replaces the worst draft blocks with transformer outputs, which acts as quality filtering — keeping high-quality drafts and only re-generating low-quality ones.

### Reproducing Our Method

Conda environment: `/rscratch/yuezhouhu/realtime-video/myenv`

`sample_run.py` reads prompts from `MovieGenVideoBench.txt` (1003 prompts available). Control the number of prompts with `NUM_PROMPTS` env var (default 200). The script supports **resume**: it skips already-generated videos, so you can safely re-run after interruptions.

**1. Reward v2.5 dynamic (default)**
```bash
cd /rscratch/yuezhouhu/realtime-video
conda activate /rscratch/yuezhouhu/realtime-video/myenv
OUTPUT_DIR=outputs/reward_dynamic NUM_PROMPTS=200 CUDA_VISIBLE_DEVICES=4,5 python sample_run.py

# Speed benchmark (10 prompts)
OUTPUT_DIR=outputs/bench_dynamic CUDA_VISIBLE_DEVICES=4,5 python benchmark_run.py

# VisionReward evaluation (1 GPU needed)
cd /rscratch/yuezhouhu/VisionReward
VIDEO_DIR=/rscratch/yuezhouhu/realtime-video/outputs/reward_dynamic NUM_PROMPTS=200 EVAL_OUTPUT=eval_dynamic_200.json CUDA_VISIBLE_DEVICES=7 python evaluate_batch.py
```

**2. Reward v2.5 fixed threshold**
```bash
cd /rscratch/yuezhouhu/realtime-video
conda activate /rscratch/yuezhouhu/realtime-video/myenv
REWARD_THRESHOLD_MODE=fixed OUTPUT_DIR=outputs/reward_fixed NUM_PROMPTS=200 CUDA_VISIBLE_DEVICES=4,5 python sample_run.py

# With custom threshold
REWARD_THRESHOLD_MODE=fixed REWARD_FIXED_THRESHOLD=-0.5 OUTPUT_DIR=outputs/reward_fixed_custom NUM_PROMPTS=200 CUDA_VISIBLE_DEVICES=4,5 python sample_run.py

# Speed benchmark (10 prompts)
REWARD_THRESHOLD_MODE=fixed OUTPUT_DIR=outputs/bench_fixed CUDA_VISIBLE_DEVICES=4,5 python benchmark_run.py

# VisionReward evaluation
cd /rscratch/yuezhouhu/VisionReward
VIDEO_DIR=/rscratch/yuezhouhu/realtime-video/outputs/reward_fixed NUM_PROMPTS=200 EVAL_OUTPUT=eval_fixed_200.json CUDA_VISIBLE_DEVICES=7 python evaluate_batch.py
```

**Running modes in parallel** (recommended — saves significant time):
```bash
# Run dynamic and fixed on separate GPU pairs simultaneously
OUTPUT_DIR=outputs/reward_dynamic NUM_PROMPTS=200 CUDA_VISIBLE_DEVICES=2,3 nohup python -u sample_run.py > logs/dynamic.log 2>&1 &
REWARD_THRESHOLD_MODE=fixed OUTPUT_DIR=outputs/reward_fixed NUM_PROMPTS=200 CUDA_VISIBLE_DEVICES=4,5 nohup python -u sample_run.py > logs/fixed.log 2>&1 &

# Evaluations can run in parallel on separate GPUs
cd /rscratch/yuezhouhu/VisionReward
VIDEO_DIR=.../outputs/reward_dynamic NUM_PROMPTS=200 EVAL_OUTPUT=eval_dynamic_200.json CUDA_VISIBLE_DEVICES=4 nohup python -u evaluate_batch.py > eval_dynamic.log 2>&1 &
VIDEO_DIR=.../outputs/reward_fixed NUM_PROMPTS=200 EVAL_OUTPUT=eval_fixed_200.json CUDA_VISIBLE_DEVICES=5 nohup python -u evaluate_batch.py > eval_fixed.log 2>&1 &
```

**Approximate timings** (RTX A6000, 200 prompts, 832×480):
- Generation: reward ~71s/video (dynamic), similar for fixed
- Each generation run requires 2 GPUs (~34GB + ~22GB)
- VisionReward evaluation: ~12s/video/GPU (29 VQA questions per video), requires 1 GPU
- The first video includes `torch.compile` warmup (~extra 100s)

**Existing outputs**: 200-prompt results are stored in `outputs/reward_v2/`. Evaluation JSON files are in `/rscratch/yuezhouhu/VisionReward/eval_reward_200.json`.

## Architecture

### Data flow for real-time generation
1. Client connects via WebSocket to `/session/{id}` in `release_server.py`
2. Server calls text encoder (`WanTextEncoder` in `utils/wan_wrapper.py`) to embed the prompt on `DIFFUSION_GPU+1`
3. `CausalInferencePipeline` (`pipeline/causal_inference.py`) generates latents block-by-block (3 frames per block) on `DIFFUSION_GPU`
4. VAE decoder (`demo_utils/vae_block3.py`) converts latents → pixel frames on `DIFFUSION_GPU+1`
5. Frames are serialized via msgpack and streamed back to the client

### Multi-GPU split
- `DIFFUSION_GPU` (default 0): transformer/diffusion model
- `DIFFUSION_GPU+1`: text encoder (UMT5-XXL) and VAE

Multi-GPU example:
```bash
CUDA_VISIBLE_DEVICES=6,7 DIFFUSION_GPU=0 uvicorn release_server:app --host 0.0.0.0 --port 8000
# GPU 6 → diffusion, GPU 7 → text encoder + VAE
```

### Inference pipelines (`pipeline/`)

Four inference pipeline variants, all block-based with `denoising_step_list` and `num_frame_per_block`:
- **CausalInferencePipeline** — forward-only generation with KV caching (primary for server)
- **BidirectionalInferencePipeline** — non-causal generation
- **CausalDiffusionInferencePipeline** — diffusion-based causal variant
- **BidirectionalDiffusionInferencePipeline** — diffusion-based bidirectional variant

Plus `SelfForcingTrainingPipeline` for multi-block training with distributed rank synchronization.

### Training model architecture (`model/`)

All training models inherit `BaseModel` → `SelfForcingModel` with three sub-networks:
- **generator** (trainable): the causal Wan2.1 model being distilled
- **fake_score** (trainable): discriminator/critic
- **real_score** (frozen): reference teacher model

Distillation strategies:
| Model | Loss approach |
|---|---|
| `DMDModel` | KL divergence distribution matching between real/fake score outputs |
| `GANModel` | Relativistic GAN loss with classifier branch, R1/R2 regularization |
| `SiDModel` | Self-improving distillation variant |
| `ODERegressionModel` | Curriculum learning from precomputed ODE trajectories |
| `CausVidModel` | Causal video generation variant |

### Configuration system
Configs are merged at load time: `default_config.yaml` → model-specific YAML (e.g., `self_forcing_server_14b.yaml`). Use `load_merge_config()` from `release_server.py` or `sample.py`. The active config is controlled by the `CONFIG` env var.

Key config fields: `denoising_step_list`, `num_frame_per_block`, `timestep_shift`, `guidance_scale`, `num_training_frames`, `causal`, `warp_denoising_step`, `mixed_precision`.

### Code conventions
- All inference runs inside `torch.set_grad_enabled(False)` / `@torch.inference_mode()`
- Models loaded in `bfloat16`; optional fp8 via `enable_fp8` config flag
- Naming: `CamelCase` classes, `snake_case` functions, `SCREAMING_SNAKE_CASE` constants, `_underscore` private methods
- Config via `omegaconf.OmegaConf`; API validation via `pydantic.BaseModel`
- `pyrightconfig.json` has type checking disabled — type hints are encouraged but unenforced
- `torch._dynamo.config.recompile_limit = 32` set in release_server.py for compile stability

### Global mutable state in `release_server.py`
`session_frames_storage`, `DO_COMPILE`, `_routing_stats`, and GPU stream objects (`upload_stream`, `download_stream`) are module-level globals. `_routing_stats` accumulates ImageReward scores across all prompts for the running-percentile threshold. Use `reset_routing_stats()` to clear between runs (called automatically in `sample.py`). Be careful when modifying server startup logic.
